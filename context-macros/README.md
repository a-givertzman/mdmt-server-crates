# context_macros

Макросы автоматизирующие работу с `RawContext` приложения `mdmt-server`
- Запись, чтение полей `RawContext`
- Загрузка полей `RawContext` из итератора элементов `<String, JsonVal>`.

## Обязательные сигнатуры потребителя

`ContextAccess` адресует `crate::domain::ContextTransaction`, поле `state`
которого содержит структуру с derive. Трейты находятся в `crate::domain`.
Образец их определений: `integration/context_traits.rs`.

```rust
pub trait ContextRead<T> {
    fn read(&self) -> Option<T>;
}
pub trait ContextReadRef<T> {
    fn read_ref(&self) -> Option<&T>;
}
pub trait ContextWrite<T>: Sized {
    fn write(self, value: T) -> Result<Self, sal_core::error::Error>;
}
pub trait IecId {
    fn iec_id() -> &'static str;
}
pub trait Properties {
    fn properties(&self) -> Result<Vec<(String, JsonVal)>, sal_core::error::Error>;
}
```

Это необходимые изменения относительно старых сигнатур: чтение возвращает
`Option`, а сериализация — `Result`. Сам derive не может изменить определение
трейта в приложении. При интеграции обнови определения и обработку результата
`properties()` у потребителей. Ошибка сериализации сохраняется как `sal_core::error::Error`.

Для кода потребителя нужны `serde`, `serde_json` и существующий `sal_core`.
Зависимости `serde`/`serde_json` в Cargo.toml этого proc-macro crate являются
тестовыми: сгенерированный код использует зависимости вызывающего crate.

## ContextAccess

| Флаг | Генерация |
| --- | --- |
| `read` | `ContextRead<T>` и `ContextReadRef<T>` |
| `read_ref` | Только `ContextReadRef<T>`, без требования `Clone` |
| `write` | `ContextWrite<T>` |
| `skip` | Запрет всех реализаций доступа для поля |
| `skip_load` | На доступ не влияет; используется `ContextLoad` |

`read` оставлен сокращением для обоих способов чтения: это сохраняет
поведение прежнего макроса и соответствует примеру документации с
`#[context(read, write)]`, из которого затем вызывают `read_ref()`.
Явный `#[context(read, read_ref, write)]` также корректен.

Порядок флагов не влияет на результат. `skip` имеет приоритет над флагами
доступа независимо от порядка. Повторные флаги дают диагностическое сообщение компилятора.

| Поле | `read()` | `read_ref()` | `write(value)` |
| --- | --- | --- | --- |
| `T` | `Some(clone)` | `Some(&field)` | Заменяет поле на `value` |
| `Option<T>` | `None` или `Some(clone)` | `None` или `Some(&value)` | Заменяет поле на `Some(value)` |

Запись принимает транзакцию по значению и возвращает `Ok(self)`.
Сигнатура `Result` сохранена для существующей цепочки расчётных шагов.
Само присваивание не вводит дополнительных ошибок или валидации.
Чтение по значению требует `Clone`; отдельное ссылочное чтение и запись — нет.
Очистка optional-поля не добавлялась: `ContextWrite<T>` принимает `T`.

Пример чтения теперь соответствует расчётной документации:

```rust
let geometry: &HullGeometry = ctx.read_ref()
    .ok_or_else(|| error.pass_with("Failed to read geometry from context"))?;
```

Для вызова методом соответствующие трейты нужно импортировать в модуль шага.

Доступ остаётся типизированным по типу значения. Два поля, претендующие на
одинаковую реализацию одного трейта, диагностируются как неоднозначность.
Независимые доступы разрешены: чтение одного поля и запись другого того же
типа допустимы, если не возникает совпадения реализуемого трейта.

`ContextAccess` предназначен для структуры с именованными полями без generic
параметров, поскольку целевая транзакция задана фиксированным типом.
Неподдерживаемые формы получают понятную ошибку.

## ContextProperties

Нужен единственный непустой `#[iec_id = "..."]`. Макрос реализует `IecId`
и `Properties` для значения и ссылки. Элемент контекста сериализуется по полям, каждое поле в пару `<iec_id, JsonVal>`, ключи формируются как `iec_id + field_name`.

Ошибки сериализации возвращаются через `Err`, без `expect`.
Generics, lifetimes, const generics и исходные `where` сохраняются.
Ограничение `Serialize` относится только к реализации `Properties`,
получение IEC-ключа сериализации не требует.

## ContextLoad

Метод называется `with_snapshot`, как в исходном коде и тесте. Упоминание
`from_snapshot` в присланном design doc не соответствует этому API.

Принимаются пары `(String, serde_json::Value)`, возвращается `(Self, Report)`.
Сохраняется частичная загрузка: корректные значения применяются, остальные
поля остаются прежними. Ошибки возвращаются в `report.errors`.

- `skip_load` исключает поле, включая требования `IecId` и десериализации.
- `skip` сам по себе загрузку не отключает.
- Отсутствие всех ключей элемента сохраняет прежнее поле и попадает в `missing_in_db`.
- Неуспешная десериализация сохраняет прежнее поле и попадает в `errors`.
- Повторный входной IEC-ключ не применяется: ни одно из его значений не выбирается.
- Одинаковые IEC-ключи разных загружаемых полей не применяются к этим полям.
- Коллизии ключей попадают в `errors`; затронутые поля сохраняют прежнее состояние.
- `unused_in_db` сортируется; порядок остальных категорий определён обходом
  полей, а ошибок коллизий — сортировкой ключей.
- `is_clean()` означает только отсутствие ошибок; missing/unused не считаются ошибками.

Для optional-поля десериализуется `T`, затем записывается `Some(T)`.
JSON `null` не является командой очистки: он проходит десериализацию в `T`.
Для `Draft` или `Displacement` это ошибка; для типа, принимающего null,
поведение определяется его десериализатором.

`ContextProperties` возвращает JSON-Value» — точнее Result<Vec<(String, JsonVal)>, Error>, где JsonVal = serde_json::Value.

Отчёт имеет видимость исходной структуры. `ContextLoad` поддерживает generic
структуры; ограничения загрузки накладываются только на загружаемые типы.

## Распознавание типов

Единый помощник распознаёт `Option<T>`, `std::option::Option<T>` и
`core::option::Option<T>`, включая абсолютные стандартные пути.
`custom::Option<T>` обрабатывается как обычный тип.

Derive работает с синтаксисом и не разрешает алиасы или импорты. Для
optional-полей используй стандартные написания; одинаковые типы значений
в полях записывай одинаково. Конфликты через алиасы дополнительно выявляет
сам компилятор при проверке реализаций трейтов.

## Проверка

Добавлены тесты поведения сгенерированного кода и тесты разбора/диагностики.
Тестовые трейты и минимальная транзакция находятся только в тестовой сборке;
они не заменяют реализации приложения.

Компиляция и тесты здесь не запускались по указанию пользователя.
Для локальной проверки:

```bash
cargo test
```

В рабочих исходниках нет `panic!`, `unwrap` или `expect` для обработки
отсутствующих значений, ошибок сериализации и некорректного derive-входа.
`unwrap` в тестах используется только для проверяемых успешных операций.
